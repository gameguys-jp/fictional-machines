# Fictional Machines 文書管理

この skill は、Fictional Machines の個別プロジェクトの文書を、共通のルールに沿って管理するための手順です。

## 最初に読むもの

1. **ルールの本文**：この skill のベースディレクトリから `../../Documentation_Rules.md`。ディレクトリ構成、文書の種類と境界、記述ステータス、史実と架空の境界、ファイルと書式、決定と課題の流れが書いてある。作業の前に必ず読む。
2. **分類体系**：`../../Fictional_Machines.md`（英語版は `../../Fictional_Machines.en.md`）。F・T・D・L・E・M・S・V・N の定義と、§07 の共通記述フォーマット。
3. **プロジェクトの `CLAUDE.md`**：プロジェクト固有のルール（分類、正となる仕様のパス、未確定項目）。ルール本文と食い違うときは、プロジェクトの `CLAUDE.md` を優先し、食い違いをユーザーに伝える。

## 作業の手順

1. **書く内容の種類を決める。** 仕様・物語・部品・デザイン・実装・決定・課題のどれか。複数にまたがるなら、種類ごとに分けて書き、リンクで結ぶ。
2. **正となる場所を探す。** 同じ内容がすでにあるなら、そこを更新する。書き写さない。
3. **新しい文書は雛形から作る。** 雛形はこの skill の `templates/` にある。

   | 作るもの | 雛形 |
   |---|---|
   | プロジェクト概要 | `templates/README.md` |
   | 仕様 | `templates/spec.md` |
   | 物語・設定 | `templates/story.md` |
   | 部品台帳 | `templates/part.md` |
   | 製品デザイン | `templates/design.md` |
   | 実装 | `templates/impl.md` |
   | 決定記録 | `templates/decisions.md` |
   | 課題台帳 | `templates/open-issues.md` |

4. **記述ステータスを付ける。** 仕様・部品・実装は `[D]`・`[P]`・`[O]`・`[V]`。物語・デザインは `[確定]`・`[仮]`・`[没]`、物語の中の事実は `[史実]`（出典へリンク）・`[架空]`。
5. **決定と課題を流す。** 不整合や未確認は `open-issues.md` に `OI-` で登録する。決めたことは `decisions.md` に `DR-` で、理由と却下した案とともに書く。反映したら課題を「解決」にして決定へリンクする。
6. **版と日付を更新する。** 内容が変わった文書は、冒頭の版と日付を上げる。英語版（`.en.md`）があれば同じコミットで更新する。

## 守ること

- 実在の人物の名前を物語に出さない。役割で書く。
- 実在の記録と矛盾させない。架空の部分は明記する。
- プロジェクトが未確定としている名称・社名・製品名・筐体・ロゴ・UI などを、決定記録を経ずに確定させない。
- 時代的制約（T2 など）があるプロジェクトでは、指定時点以前の資料だけを年代の根拠にする。
- 公開リポジトリでは、個人情報・ローカルの絶対パス・トークン・資料の PDF を入れない。一時フォルダは `<scratchpad>` と書く。コミット前に走査する。

## 移行するとき

既存の文書をこの構成に移すときは、次の順で進める。

1. 既存の文書を種類ごとに分類し、移動先の一覧をユーザーに示す。
2. 移動はファイル単位で行い、`git mv` で履歴を残す。
3. 1つの文書に複数の種類が混ざっている場合（例：仕様書の中の開発史）は、該当部分を正しい種類の文書へ移し、元の場所にはリンクを残す。
4. 文書間のリンクと、`CLAUDE.md` に書かれたパスを更新する。
5. これまでの決定のうち記録がないものを、`decisions.md` に起こす。

## 実装を始めるとき

エミュレータ・FPGA・PCB・SDK などのコードやデータを作り始めるときは、次の順で進める。

1. ルール本文の §10「リポジトリ構成（実装）」に従い、使うフォルダだけを作る（`emulator/`、`firmware/`、`sdk/`、`hardware/fpga/` など）。
2. `docs/impl/<名前>.md` を雛形 `templates/impl.md` から作り、M・S・V の現状と目標を書く。
3. コードで使う定義（アドレスマップ、レジスタ表など）を、機械が読める形で `docs/spec/` に1か所置く。実装はそこから生成するか参照する。仕様を書き写さない。
4. 外部のコードを使う前に、出所・版・ライセンスを確かめ、`third_party/` に元のライセンスのまま置く。組み込んだ成果物のライセンスの扱いが未決なら、課題台帳に登録する。
5. ビルドとテストのコマンドを、プロジェクトの `CLAUDE.md` に書く。
